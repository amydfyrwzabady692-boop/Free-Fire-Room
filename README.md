# Free Fire Room

سامانهٔ چندمستاجری برای مدیریت و اطلاع‌رسانی کاستوم‌های جایزه‌دار Free Fire. شامل ربات تلگرام، API، پنل برگزارکننده، پنل Super Admin، زمان‌بندی ارسال رمز اتاق، و Audit Log.

**این محصول شریک رسمی Garena / Free Fire نیست.** برگزارکننده مسئول قانونی بودن مسابقه و تحویل جایزه است. نسخهٔ اول خرید اجباری، شرط‌بندی یا پرداخت ندارد.

## فرض‌های قابل‌تغییر

اگر هنگام راه‌اندازی مقدار واقعی ندادید، این پیش‌فرض‌ها استفاده می‌شود:

| مورد | فرض |
|---|---|
| دامنه | `http://localhost:8080` (توسعه) |
| حالت تلگرام | `polling` در توسعه، `webhook` در تولید |
| منطقه زمانی پیش‌فرض | `Asia/Tehran` (ذخیرهٔ تاریخ‌ها همیشه UTC) |
| تأیید کاستوم | لازم است مگر در تنظیمات خاموش شود |
| استقرار | Docker Compose + Nginx |
| Super Admin | ساخته می‌شود با CLI، نه با مقدار سخت‌کد |

توکن ربات، کلید رمزنگاری و رمز دیتابیس **فقط** از متغیر محیطی خوانده می‌شوند.

## یک دستور روی VPS

روی سرور (اوبونتو + Docker):

```bash
git clone https://github.com/amydfyrwzabady692-boop/Free-Fire-Room.git
cd Free-Fire-Room
cp .env.example .env
nano .env   # حداقل این سه تا را پر کن
chmod +x deploy.sh
./deploy.sh
```

حداقل فیلدهای `.env`:

```env
BOT_TOKEN=123456:ABC...
BOT_USERNAME=YourBotUsername
BOOTSTRAP_SUPERADMIN_TELEGRAM_ID=123456789
```

`./deploy.sh` بقیهٔ کلیدها را می‌سازد، دیتابیس را migrate می‌کند، Super Admin را می‌سازد و همهٔ کانتینرها را بالا می‌آورد.

پنل: `http://IP-SERVER`  
ورود: همان شناسه تلگرام + رمز که اسکریپت چاپ می‌کند (یا `BOOTSTRAP_SUPERADMIN_PASSWORD` در `.env`).

بعد از اولین اجرا، ربات را در تلگرام `/start` کنید و در کانال اصلی **ادمین** کنید.

## پنل مالک ربات (داخل تلگرام)

`/admin` یا دکمهٔ «پنل مالک ربات». همهٔ بخش‌ها **صفحه‌بندی‌شده** و روی یک پیام ویرایش می‌شوند
(قبلاً هر بخش ۱۰ تا ۲۰ پیام جدا می‌فرستاد و به سقف ارسال تلگرام می‌خورد).

| بخش | کاری که می‌کند |
|---|---|
| داشبورد | آمار کل + فهرست «نیاز به رسیدگی» |
| کاستوم‌های در انتظار | تأیید / رد، با اطلاع خودکار به برگزارکننده |
| برگزارکنندگان | مرتب‌شده بر اساس منتظر تأیید و سپس کم‌اعتبارترین |
| جستجوی کاربر | پروندهٔ کامل: آمار، بن، سابقهٔ اعتبار |
| کانال اجباری | افزودن، روشن/خاموش، **حذف** |
| گزارش تخلف | تأیید تخلف (کسر اعتبار)، بن برگزاری، بستن |
| برنده‌ها | دیدن اسکرین‌شات، تأیید یا رد ادعا |
| همه کاستوم‌ها | برای هر کاستوم: **قیف کامل** و لغو اضطراری |

## امتیاز اعتبار برگزارکننده

جدول `organizer_trust_events` و ستون `organizers.trust_score` از ابتدا وجود داشتند ولی
هیچ‌جا نوشته نمی‌شدند. حالا هر رویداد امتیاز را جابه‌جا می‌کند و یک ردیف قابل حسابرسی
با دلیلش ثبت می‌شود:

| رویداد | تغییر |
|---|---|
| ارسال موفق ROOM ID / PASS | +۶ |
| نفرستادن مشخصات در مهلت | −۱۸ |
| گزارش تأییدشدهٔ «جایزه نداد» | −۱۴ |
| گزارش تخلف تأییدشده | −۱۰ |
| تأیید پرداخت جایزه | +۴ |

امتیاز بین ۰ تا ۱۰۰ محدود می‌شود و زیر ۳۰ به بازیکن **هشدار** نشان داده می‌شود.

## زمان کاستوم دست برگزارکننده است

هیچ‌چیز کاستوم را ساعت نمی‌بندد. کاستوم تا وقتی در «کاستوم‌های پیش‌رو» می‌ماند و
ثبت‌نام و ارسال ROOM ID / PASS باز است که برگزارکننده خودش دکمهٔ
**«کاستوم شروع شد — انتقال به گذشته»** را در «کاستوم‌ها و آمار من» بزند.

| قبل | حالا |
|---|---|
| ساعت شروع باید حداقل ۱۰ دقیقه بعد باشد | هر ساعتی از الان به بعد |
| انتخاب روز فقط تا ۳ روز | تا ۵ روز |
| حداکثر ۵ کانال جوین اجباری | تا ۸ کانال |
| فقط یک پیج فالو | تا ۵ پیج، هرکدام با اسکرین جدا |
| مهلت ارسال مشخصات: ۵ دقیقه بعد از شروع | تا وقتی «کاستوم شروع شد» زده نشود |
| پر شدن کاستوم: ۲۰ دقیقه بعد از شروع | تا وقتی «کاستوم شروع شد» زده نشود |
| بعد از ساعت شروع خودکار به «گذشته» می‌رفت | فقط با دکمهٔ برگزارکننده (یا ۳۰ دقیقه پشتیبان) |
| ظرفیت ۱۰۰ نفر | بدون محدودیت |

ستون `events.archived_at` (مهاجرت `0008`) تنها معیار «گذشته» است. تنها استثنا
`AUTO_ARCHIVE_MINUTES` (پیش‌فرض ۳۰ دقیقه بعد از ساعت شروع) است: پشتیبان کسی که
هیچ‌وقت دکمه را نمی‌زند، تا کاستومی برای همیشه در فهرست نماند.

تا آن لحظه **هر کسی که شرایط را کامل کند بلافاصله ROOM ID / PASS می‌گیرد** — چه سر
ساعت آمده باشد، چه بعد از اینکه برگزارکننده مشخصات را داده و دست چند نفر رسیده و
تازه ثبت‌نام کرده. این کار را `queue_late_credentials()` انجام می‌دهد و از سه جا صدا
زده می‌شود: دکمهٔ «عضو شدم»، «بررسی مجدد»، و لحظه‌ای که بازیکن آخرین اسکرین فالو را
می‌فرستد. زمان‌بند دوره‌ای فقط تور ایمنی است، نه مسیر اصلی.

ظرفیت `0` یعنی نامحدود؛ کاستوم‌های ساخته‌شده در ربات همین‌طورند و کاستوم‌های زندهٔ
قبلی هم در مهاجرت `0008` به همین حالت منتقل می‌شوند.

## اطلاع‌رسانی: لحظهٔ ثبت، یک ساعت قبل، ده دقیقه قبل

هر کاستوم جایزه‌دار سه بار به **همهٔ کاربران ربات** اعلام می‌شود:

| کِی | به چه کسی | چه می‌گوید |
|---|---|---|
| لحظهٔ انتشار | همه به‌جز خود برگزارکننده | کاستوم جدید + جایزه + ساعت + دکمهٔ ورود |
| ۱ ساعت قبل | ثبت‌نام‌نکرده‌ها | همان دعوت |
| ۱ ساعت قبل | ثبت‌نام‌کرده‌ها | «فقط در کانال‌ها بمانید» |
| ۱۰ دقیقه قبل | هر دو گروه | همان، با فاصلهٔ ده دقیقه |

هر ارسال یک قفل Redis می‌گیرد تا دوبار نرود، با سرعت `TELEGRAM_OUTBOUND_PER_SECOND`
فرستاده می‌شود و `TelegramRetryAfter` را رعایت می‌کند.
`EVENT_REMINDER_BROADCAST=false` هر سه را خاموش می‌کند و فقط ثبت‌نام‌کرده‌ها یادآوری
می‌گیرند.

فاصله‌ها از `reminder_offsets_minutes` هر کاستوم می‌آید (پیش‌فرض `[60, 10]`)؛ اگر
کاستوم کمتر از یک ساعت مانده به شروع ساخته شود، فقط یادآوری ده‌دقیقه‌ای ثبت می‌شود.
متن «۱ ساعت» از خود جاب خوانده می‌شود نه از ساعت — زمان‌بند هر ۶۰ ثانیه تیک می‌زند و
اندازه‌گیری هر بار «۵۹ دقیقه» می‌نوشت.

## چند پیج فالو، نه یکی

مهاجرت `0009` جدول `event_social_tasks` را اضافه می‌کند: هر کاستوم می‌تواند **تا ۵ پیج**
اینستاگرام/یوتیوب بخواهد، و بازیکن **برای هر پیج یک اسکرین جدا** می‌فرستد.
`social_proofs.task_id` می‌گوید هر اسکرین مال کدام پیج است، پس برگزارکننده می‌بیند
دقیقاً کدام پیج را رد کرده.

`events.social_url` هنوز پیج اول را نگه می‌دارد تا `social_required()` یک خواندن
ستون ساده بماند؛ فهرست کامل در جدول جدید است. مهاجرت، پیج تکیِ کاستوم‌های قبلی و
اسکرین‌های جمع‌شده را خودش به رکورد جدید وصل می‌کند.

ثبت‌نام وقتی قطعی می‌شود که برای **همهٔ** پیج‌ها اسکرین فرستاده شده باشد و هیچ‌کدام رد
نشده باشد — هم موقع ثبت‌نام بررسی می‌شود، هم دوباره لحظهٔ ارسال ROOM ID / PASS.

## دکمهٔ «شروع کاستوم»

در پنل برگزارکننده یک ورودی جدا دارد: کاستوم را از فهرست انتخاب می‌کنید، خلاصه و آمارش
را می‌بینید، و بعد تأیید می‌کنید. همان دکمه زیر کارت هر کاستوم در «کاستوم‌ها و آمار من»
هم هست.

## فالو اینستاگرام / یوتیوب: فرستادن کافی است

برگزارکننده هنگام ثبت کاستوم می‌تواند آدرس پیج بدهد یا «رد کردن» را بزند. اگر بدهد،
این مرحلهٔ **بعد از** جوین کانال‌های اجباری است — نه کنارش:

```
جوین کانال‌ها → «عضو شدم» → ارسال اسکرین هر پیج → ثبت‌نام قطعی (بدون انتظار)
```

**هیچ تأییدی لازم نیست.** لحظه‌ای که آخرین اسکرین می‌رسد، `register_user` دوباره اجرا
می‌شود و `queue_late_credentials` مشخصات را راه می‌اندازد؛ بازیکن منتظر کسی نمی‌ماند.

گیت یک تابع خالص است، `gate_from(tasks, proofs)`، که هر دو نسخهٔ async و sync صدایش
می‌زنند تا از هم جدا نیفتند. شرطش «رد نشده» است، نه «تأیید شده»:

| وضعیت اسکرین | گیت | یعنی |
|---|---|---|
| نیست | ❌ | هنوز نفرستاده |
| `pending` | ✅ | فرستاده و کسی نگاهش نکرده — همین کافی است |
| `approved` | ✅ | فرستاده و برگزارکننده هم دیده |
| `rejected` | ❌ | برگزارکننده ردش کرده؛ تا اسکرین درست نفرستد چیزی نمی‌گیرد |

این تغییر **مهاجرت ندارد**: هر سه وضعیت سر جایشان‌اند و فقط معنی «کافی بودن» عوض شده.

### بخش «اسکرین‌های فالو» در پنل برگزارکننده

صف قبلی فقط `pending`ها را نشان می‌داد، پس وقتی هیچ‌چیز تأیید نمی‌شود هرگز خالی
نمی‌شد و بعد از تأیید هم اصلاً باز نمی‌شد. حالا یک **بایگانی** است:

- یک پیام که در جا ویرایش می‌شود، نه ۱۲ پیام پشت سر هم (تلگرام آن‌ها را گلوگاه می‌کند)
- صفحه‌بندی ۵تایی در خود دیتابیس، با ترتیب قطعی `(created_at DESC, id DESC)`
- فیلتر «همه / رد شده / بررسی‌نشده»
- «دیدن اسکرین N» عکس را کامل باز می‌کند، با «رد این اسکرین — ورودش باطل شود» زیرش
- روی یک اسکرینِ ردشده، دکمه می‌شود «اشتباه رد شد — قبولش کن»

**رد کردن واقعاً چیزی را پس می‌گیرد.** `_void_registration` ثبت‌نام را `INELIGIBLE`
می‌کند، `confirmed_count` را کم می‌کند و اگر کاستوم `FULL` بود به `PUBLISHED` برمی‌گرداند.
اگر ROOM ID / PASS از قبل رفته باشد، به بازیکن صریح گفته می‌شود ورودش **باطل** شده.

دو دکمهٔ گروهی مانده‌اند و عمداً نامتقارن‌اند: «همه درست بود» فقط `pending`ها را
«بررسی‌شده» علامت می‌زند و برای هیچ‌کس چیزی عوض نمی‌کند (پس ارزان است)، ولی «رد همه»
از یک صفحهٔ تأیید رد می‌شود چون یک تپ اشتباه کل کاستوم را باطل می‌کند. هر دو سقف
۶۰تایی دارند: حلقهٔ قبلی برای ۲۰۰ نفر `register_user` صدا می‌زد و آن یعنی حدود ۲۰۰۰
درخواست `getChatMember` داخل یک هندلر.

## اسکرین فالو همراه اسکرین برنده

وقتی بازیکنی ادعای برنده می‌کند، اسکرین‌های فالویی که قبلاً فرستاده بود **همان لحظه**
برای برگزارکننده می‌روند، درست قبل از اسکرین برد:

```
سرصفحه («۲ اسکرین در ادامه می‌آید») → اسکرین پیج ۱ → اسکرین پیج ۲ → اسکرین برنده
```

اسکرین برد **آخر** می‌رود تا دکمه‌های «تأیید برنده / رد / پیام» بالای کادر تایپ بماند و
زیر انبوه عکس‌ها گم نشود. آلبوم (`sendMediaGroup`) عمداً استفاده نشده: تلگرام به آلبوم
`reply_markup` نمی‌چسباند، یعنی برگزارکننده نمی‌توانست همان‌جا اسکرین جعلی را رد کند.

اسکرین‌های **ردشده هم** فرستاده می‌شوند — دقیقاً همان چیزی است که موقع قضاوت یک ادعا
باید دیده شود. اگر کاستوم شرط فالو داشته و بازیکن هیچ اسکرینی نفرستاده، به‌جای سکوت
یک هشدار صریح می‌آید.

ترتیب اسکرین‌ها بر اساس `sort_order` پیج است، نه زمان ثبت: سه اسکرین که در یک لحظه
`flush` می‌شوند `created_at` یکسان می‌گیرند و ترتیبشان به UUID تصادفی می‌افتد — آن وقت
«اسکرین ۱ از ۳» هر بار پیج دیگری را نام می‌برد.

سرعت ارسال با `telegram_ops.pace()` تنظیم می‌شود؛ همان تابع حالا تنها تعریف
`get_outbound_rate` در ورکرها هم هست، تا یک هندلر مجبور نباشد ماژول Celery را ایمپورت کند.

## بنر کاستوم و انتشار در کانال

پست کانال **متن است، نه عکس**. یک پیام متنی روی هر گوشی خوانا می‌ماند، فوروارد و
نقل‌قول می‌شود، و چشم خواننده اول روی جایزه می‌نشیند نه روی طرح گرافیکی.

زیر هر کاستوم دکمهٔ **«انتشار بنر در کانال»** هست:

1. ربات متن پست را از روی همان ورودی‌های ویزارد می‌سازد
2. دقیقاً همان پیام را اول در پی‌وی خود برگزارکننده می‌فرستد (پیش‌نمایش، نه ارسال)
3. با تأیید، در کانال کاستوم منتشر می‌شود

پست دقیقاً همان شکلی است که مالک ربات خواسته:

```
🚨 کاستـوم جایـزه دار

🥇نفر اول:  واریز یک میلیون به کارت
🥈نفر دوم:  ۵۰۰ هزار تومان

زمان کاستوم 👇🔥

امشب ساعت ۲۲ ⚡

شرایط و قوانین ❗

✔️چیــت و تبــانی ممنوع 👎
✔️ عضویت در ۳ کانال اجباری
✔️ فالو ۲ پیج + ارسال اسکرین‌شات
✔️ ROOM ID و PASS فقط داخل ربات می‌آید

موفق و پیروز باشین 🥰
```

زیرش یک دکمهٔ URL با متن **دقیقِ** «ورود به کاستوم جایزه دار» که به
`?start=event_<token>` وصل است — هر کس در کانال بزند، مستقیم داخل ربات باز می‌شود.
آن دکمه با `InlineKeyboardButton` خام ساخته می‌شود نه با `ibtn()`: `ibtn` وقتی aiogram
پارامتر `style` را نپذیرد یک دایرهٔ رنگی به اول متن می‌چسباند و متن دیگر دقیق نیست.

**جایزه به نفرات تقسیم می‌شود** بدون هیچ مرحلهٔ اضافه در ویزارد: هر خطِ متن جایزه یک
نفر است. یک خط یعنی یک جایزه، سه خط یعنی «نفر اول / نفر دوم / نفر سوم». متن مرحلهٔ
جایزه هم همین را می‌گوید.

چند نکتهٔ ریز:

- همه‌جا **رقم فارسی**. سطر ساعت از قبل «۲۲:۰۰» بود؛ پستی که کنارش «3 کانال» بنویسد
  انگار دو نفر نوشته‌اندش.
- `POST_LIMIT` سقف تلگرام نیست (پیام متنی تا ۴۰۹۶ جا دارد) — سقف **مرتب ماندن** است.
  هر تکه جدا کوتاه می‌شود (هر خط جایزه تا ۱۲۰، توضیح تا ۲۰۰)، پس این سقف فقط ضربه‌گیر
  است و هیچ‌وقت وسط یک تگ HTML نمی‌بُرد.
- هر رشتهٔ ورودی برگزارکننده از `esc()` رد می‌شود؛ حالت پیش‌فرض ربات HTML است و یک `<`
  در متن جایزه کل ارسال را می‌شکست.
- `app/services/posters.py` (تولیدکنندهٔ پوستر Pillow) دوباره **بدون مصرف‌کننده** است و
  از `organizer.py` ایمپورت نمی‌شود، پس Pillow اصلاً داخل پروسهٔ ربات بار نمی‌شود.

قبل از ارسال، `inspect_bot_admin` دوباره از تلگرام می‌پرسد؛ `bot_is_admin` فقط موقع وصل
کردن کانال نوشته می‌شود و ممکن است ساعت‌ها کهنه باشد.


## برنده، آیدی جایزه و گفت‌وگوی دوطرفه

- برگزارکننده هنگام ثبت کاستوم یک **آیدی دریافت جایزه** می‌دهد (`@my_id`). دفعهٔ بعد
  با یک دکمه همان را انتخاب می‌کند، یا از «آیدی دریافت جایزه» در پنل عوضش می‌کند.
- اسکرین ادعای برنده با دکمه‌های **تأیید برنده / رد / پیام به برنده** برای برگزارکننده
  و مالک ربات می‌رود؛ آیدی و یوزرنیم بازیکن هم کنارش هست تا بشود مستقیم پی‌وی داد.
- با تأیید، ربات آیدی دریافت جایزه را برای برنده می‌فرستد به‌همراه دکمهٔ رفتن به پی‌وی.
- هر دو طرف می‌توانند **داخل ربات** جواب بدهند: «پیام به برنده» و «پاسخ به برگزارکننده».
  هر پیام در `winner_messages` ثبت می‌شود.

## تکرار کاستوم با یک دکمه

بیشتر برگزارکننده‌ها هر شب همان کاستوم را می‌گذارند. زیر هر کاستوم در «کاستوم‌ها و آمار
من» دکمهٔ **تکرار** هست: روز و ساعت را می‌پرسد و بقیه را از کاستوم قبلی برمی‌دارد —
کانال‌های جوین اجباری، جایزه، پیج‌های فالو، آیدی دریافت جایزه، توضیح و بنر.

`repeat_event()` عمداً **ROOM ID / PASS را کپی نمی‌کند**: اتاق قبلی دست بازیکن‌های
دفعهٔ پیش است و کپی کردنش یعنی اتاق جدید را مجانی دارند. ثبت‌نام‌ها، `confirmed_count`
و `archived_at` هم صفر شروع می‌شوند.

## پروفایل عمومی برگزارکننده

هر برگزارکننده یک لینک دارد: `?start=org_<id>`. از «پروفایل عمومی من» در پنل می‌گیردش و
در بیوی کانالش می‌گذارد. بازیکن‌ها هم از دکمهٔ «دربارهٔ برگزارکننده» روی کارت هر کاستوم
به همان صفحه می‌رسند.

پروفایل چیزهایی را نشان می‌دهد که آدم قبل از اعتماد به یک غریبه می‌خواهد بداند:

| عدد | یعنی |
|---|---|
| اعتبار | `organizers.trust_score` با برچسب فارسی |
| امتیاز از بازیکن‌ها | میانگین ستاره‌های `event_reviews` |
| کاستوم برگزار کرده | کاستوم‌های منتشرشده/تمام‌شده (لغوشده‌ها حساب نمی‌شوند) |
| ROOM ID / PASS فرستاده | کاستوم‌هایی که مشخصاتشان واقعاً ارسال شده |
| مجموع شرکت‌کننده | جمع ثبت‌نام‌های قطعی |
| لغو کرده | فقط وقتی صفر نباشد نشان داده می‌شود |

زیرش کاستوم‌های بازش دکمه می‌شوند و «نظرات بازیکن‌ها» همهٔ نظرهای او را می‌آورد، نه فقط
یک کاستوم. اگر اعتبارش زیر ۳۰ باشد، هشدار قرمز بالای کارت می‌آید.

## تعداد شرکت‌کننده روی دکمهٔ کاستوم

دکمهٔ هر کاستوم حالا `🕐 ۲۲:۰۰ · 🎁 ۱۰۰۰ الماس · 👥 ۴۷` است. کاستوم شلوغ‌تر بیشتر
اعتماد می‌آورد و همین باعث می‌شود بیشتر پر شود. وقتی هنوز کسی ثبت‌نام نکرده چیزی نشان
داده نمی‌شود (به‌جای «۰» که برعکس عمل می‌کند)، و بودجهٔ ۶۴ کاراکتری دکمه از سهم متن
جایزه کم می‌کند تا برچسب هیچ‌وقت از حد رد نشود.

## کارت کاستوم: هر بار یک کار

کارت قبلی تا ۱۰ ردیف دکمه داشت و فقط دوتایشان به وضعیت بازیکن ربط داشت — لینک
کانال‌ها، فالو، «عضو شدم»، ارسال اسکرین، برنده شدم، دربارهٔ برگزارکننده، نظر و امتیاز،
نظرات، گزارش به مالک، بازگشت. بدتر: ردیف فالو **قبل از** «عضو شدم» کشیده می‌شد.

حالا `event_detail_kb` دو پارامتر تازه دارد و کارت دو حالت دارد:

| مرحله | چه چیزی دیده می‌شود |
|---|---|
| هنوز مشغول شرایط | لینک کانال‌ها + «عضو شدم» + بازگشت |
| کانال‌ها سبز شد | «باز کردن پیج و فالو» + «ارسال اسکرین‌شات فالو» + بازگشت |
| کاستوم شروع/تمام/لغو شد | برنده شدم، دربارهٔ برگزارکننده، نظر و امتیاز، نظرات، گزارش به مالک |

- `channels_done` — ردیف فالو تا سبز شدن همهٔ کانال‌ها **اصلاً کشیده نمی‌شود**، و همیشه
  زیر «عضو شدم» است.
- `show_aftercare` — گزارش، پروفایل برگزارکننده و نظرها بعد از شروع/تمام شدن کاستوم
  می‌آیند. `rep:{token}` از جای دیگری قابل دسترس نیست، پس عمداً هر وقت کاستوم بسته یا
  مشخصات نرسیده باشد برمی‌گردد.
- لینک کانال‌ها بعد از سبز شدن حذف می‌شود؛ فقط نویز است.

هندلر `soc:` هم گارد سخت خودش را دارد: حتی اگر بازیکن از کیبورد کهنه یا یک پیام قدیمی
آن را بزند، تا عضو همهٔ کانال‌ها نشده باشد به مرحلهٔ اسکرین راه پیدا نمی‌کند. سه تست
این ترتیب را قفل می‌کنند.

## قیف هر کاستوم

`event_views` (مهاجرت `0007`) بالای قیف را ثبت می‌کند — چیزی که قبلاً اصلاً دیده نمی‌شد:

```
کارت را دیدند → وارد ثبت‌نام شدند → شرایط را کامل کردند → مشخصات را گرفتند
```

برگزارکننده از «قیف و آمار» و مالک ربات از کارت هر کاستوم می‌بیند، به‌همراه یک جملهٔ
پیشنهاد دربارهٔ بزرگ‌ترین محل ریزش. خروجی CSV شرکت‌کننده‌ها هم از همان‌جا گرفته می‌شود.

## اجرا در کنار ربات‌های دیگر روی یک VPS

حالت سبک (`--profile bot`) عمداً طوری تنظیم شده که به بقیهٔ سرور کاری نداشته باشد:

| ویژگی | مقدار |
|---|---|
| پورت باز روی هاست | **هیچ** — ربات فقط polling می‌زند |
| سقف حافظه | bot 512m + postgres 64m + redis 20m ≈ **۶۰۰ مگابایت** |
| سقف CPU ربات | ۱ هسته |
| لاگ هر کانتینر | حداکثر ۳ فایل × ۱۰ مگابایت |

لاگ‌ها سقف دارند چون درایور پیش‌فرض داکر هیچ‌وقت rotate نمی‌کند؛ روی سروری که
چند stack دارد، یک لاگ بی‌سقف دیسک را پر می‌کند و **همهٔ** کانتینرها با هم
می‌خوابند.

دستور استقرار:

```bash
cd /opt/Free-Fire-Room
git pull origin main
docker compose -f docker-compose.yml -f docker-compose.minimal.yml --profile bot up -d --build migrate bot
```

`--build migrate bot` نه فقط `bot`: مهاجرت دیتابیس داخل سرویس `migrate` اجرا
می‌شود و اگر image آن rebuild نشود، از نسخهٔ کش‌شدهٔ قدیمی اجرا می‌شود و
مهاجرت‌های جدید اعمال نمی‌شوند.

اگر ربات مدام ری‌استارت شد و در لاگ فقط `bot_step=1` و `bot_step=2` تکرار شد
بدون هیچ traceback، یعنی کرنل کشته‌اش — سقف حافظه کم است:

```bash
docker inspect free-fire-room-bot-1 --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}'
```

`OOMKilled=true` یا `ExitCode=137` یعنی `mem_limit` سرویس `bot` را باید بالاتر برد.

**دستورهایی که روی این سرور نباید بزنید:**

| دستور | چرا |
|---|---|
| `docker system prune -a` | image و شبکهٔ ربات‌های دیگر را هم پاک می‌کند |
| `docker compose down -v` | volume دیتابیس را پاک می‌کند — کل داده‌ها می‌رود |
| `--remove-orphans` | کانتینرهایی را که برچسب همین پروژه را دارند ولی در فایل نیستند حذف می‌کند |

برای دیدن اینکه فقط کانتینرهای همین پروژه دست خورده‌اند:

```bash
docker compose -f docker-compose.yml -f docker-compose.minimal.yml ps
docker ps --format 'table {{.Names}}	{{.Status}}'
```

اگر روزی پنل وب را هم بالا آوردید و پورت ۸۰ سرور قبلاً گرفته است، در `.env`
مقدار `HTTP_PORT` را عوض کنید (مثلاً `HTTP_PORT=8080`) تا با سایت موجود
تداخل نکند.

## معماری (خلاصه)

```
Telegram ── webhook/polling ──► Bot (aiogram 3) ──┐
پنل Next.js ── HTTPS/Nginx ──► FastAPI ──────────┼── PostgreSQL
Celery worker/beat ◄── Redis broker/lock/cache ──┘
```

- **FastAPI**: API، وب‌هوک، احراز هویت، RBAC
- **aiogram 3**: منوی بازیکن، ویزارد برگزارکننده، Deep Link
- **PostgreSQL**: منبع حقیقت + قفل ردیف برای ظرفیت
- **Redis**: FSM، Rate Limit، Distributed Lock، صف Celery
- **Celery Beat**: هر ۵ ثانیه Jobهای سررسیدشده را با `FOR UPDATE SKIP LOCKED` برمی‌دارد (Idempotent)
- **Fernet**: رمزنگاری Room ID / Password / TOTP secret

دلیل انتخاب Celery به‌جای فقط APScheduler: چند Worker، Restart امن، Retry و صف جدا برای broadcast.

جزئیات: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) و [docs/ERD.md](docs/ERD.md)

## مسیر پذیرش MVP

1. Super Admin از پنل «کانال‌های اجباری» کانال اصلی را اضافه کند (ربات باید ادمین باشد).
2. برگزارکننده کانال خود را وصل کند و مالکیت تأیید شود.
3. کاستوم با زمان، کانال اجباری، آیدی دریافت جایزه و در صورت تمایل شرط فالو ساخته شود (ظرفیت نامحدود).
4. مدیر کاستوم را تأیید کند.
5. بازیکن از Deep Link `https://t.me/BOT?start=event_TOKEN` وارد شود.
6. عضویت اجباری بررسی شود و اگر شرط فالو فعال باشد، تا تأیید اسکرین ثبت‌نام قطعی نشود.
7. در زمان مقرر فقط واجدین شرایط Room ID/Password را **یک‌بار** در خصوصی بگیرند.
8. لغو/تغییر زمان Jobها را به‌روز کند؛ Ban فوری اعمال شود.
9. برگزارکننده «کاستوم شروع شد» را بزند و کاستوم به «گذشته» برود.
10. برنده اسکرین بفرستد، برگزارکننده تأیید کند و آیدی دریافت جایزه برایش ارسال شود.

## Production

1. `.env` با `APP_ENV=production`، `DEBUG=false`، `TELEGRAM_MODE=webhook`، `OPENAPI_ENABLED=false`
2. `PUBLIC_BASE_URL=https://your-domain`
3. گواهی TLS را در مسیر Nginx قرار دهید
4. `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`
5. وب‌هوک: کانتینر `bot` در حالت webhook فقط webhook را ثبت می‌کند؛ آپدیت‌ها به FastAPI می‌رسند

Backup:

```powershell
docker compose exec postgres pg_dump -U ffroom ffroom > backup.sql
```

بازگردانی: `psql` روی فایل دامپ. Rollback مهاجرت: `alembic downgrade -1`
